# Architecture

## Layers

Four-layer medallion layout (RAW → STAGING → CURATED → SERVING), matching
`PROJECT_PLAN.md` §7. In this implementation, RAW/STAGING/CURATED are
computed in-memory within one Spark session per pipeline run rather than
being materialised to separate Parquet directories between every stage
(`c360/pipeline/run_pipeline.py` chains `read_raw → apply_contract_typing →
apply_cleaning → dq.evaluate → conform → identity resolve → aggregate` as
one Spark job graph, with `.cache()` at the accepted/cleaned checkpoint per
dataset). This is a **documented scope reduction** for time, not an
architectural disagreement with the spec: the boundary between typing,
cleaning, and DQ is still enforced by separate functions/modules
(`c360/pipeline/typing_clean.py`, `c360/dq/engine.py`), each independently
testable and independently callable, and the intermediate Parquet layout
described in §7.1 is the natural next step if incremental/replay semantics
are needed. See ADR-01 in `PROJECT_DECISIONS.md`.

```
generator (Python, seeded)
    -> data/input/*.csv|*.jsonl|*.jsonl.gz  (9 source files)
    -> read_raw()          all-string read + lineage columns (F-01)
    -> apply_contract_typing()   try_cast per c360/schema contract (F-02)
    -> apply_cleaning()          email/phone/country/name normalisation (F-03)
    -> dq.engine.evaluate()      6-dimension scoring, accept/warn/quarantine/reject (F-04..)
    -> person_identity_edges()   namespaced identifier long table (F-04)
    -> identity.resolve_identities()   screening -> match rules -> connected
                                        components -> guards -> canonical IDs (F-06)
    -> aggregate.py               order enrichment, customer_metrics (RFM/CLV/churn),
                                   sessionisation (F-08, F-09)
    -> loader.postgres_loader     COPY-to-staging + upsert (C-08)
    -> segments.evaluator          SQL-compiled rule AST over customer_metrics (F-11)
    -> FastAPI (c360.main)         JWT + RBAC + masking over PostgreSQL (C-10)
    -> React console                11-screen operator UI (C-11)
```

## Component map

| Component | Technology | Responsibility |
|---|---|---|
| Generator | Python, NumPy PCG64 | Reproducible synthetic data + defect injection (§5) |
| Ingestion/typing/cleaning | PySpark | All-string raw read, contract typing, normalisation |
| DQ engine | PySpark (Column expressions) | Generic rule engine, 6-dimension scoring |
| Identity resolution | PySpark | Screening, match rules, connected components, guards, canonical IDs |
| Aggregation | PySpark | Order enrichment, RFM/CLV, churn band, sessionisation |
| Loader | Python + psycopg | COPY-to-staging + upsert into PostgreSQL |
| Segmentation | Python + PostgreSQL | AST → parameterised SQL compiler, full recompute + deltas |
| API | FastAPI + SQLAlchemy Core | JWT auth, RBAC, masking, all business endpoints |
| Console | React + TypeScript + Vite | Operator UI |

## Why PySpark, where, and why not elsewhere

Per §7.4/§8.9: ingestion, typing, cleaning, DQ evaluation, identity
resolution, and aggregation all operate as column-expression passes over
the full dataset and are implemented in PySpark. The product catalogue
(≤20k rows), segment evaluation, and the entire API/serving path
deliberately are **not** — they are SQL or plain Python. The loader and API
packages import no `pyspark` symbol; `T-20`-equivalent behaviour (the API
importing without a Spark installation present) is a structural property of
the `import-linter`-style layering, though a CI job enforcing it explicitly
was not added (see `PROJECT_DECISIONS.md`).

## Why not Airflow (ADR-05)

The DAG has ~13 stages, one schedule, one executor, no backfill/SLA
requirement. `c360/pipeline/run_pipeline.py` is a single Typer command that
owns run/stage bookkeeping directly in `pipeline_runs`/`pipeline_stage_runs`.
Airflow's scheduler, metadata DB, and web server would add operational
surface without adding correctness at this scale; the production migration
path (each stage becomes an Airflow task, `pipeline_runs` becomes
informational rather than authoritative) is straightforward if the DAG
grows branching or SLA requirements.

## Why not Spark writing directly to PostgreSQL via JDBC (ADR-09)

`c360/loader/postgres_loader.py` converts the final Spark DataFrame to
pandas and uses `psycopg`'s `COPY` into a temp staging table, then a single
`INSERT ... ON CONFLICT DO UPDATE`. Direct JDBC writes from many executors
open many connections and cannot express upsert semantics natively, and
partial-failure states are hard to reason about. `COPY` + upsert is
transactional per table and keeps failure modes simple to explain.

## Identity resolution: the scaling argument

Candidate edges are generated by `groupBy(namespace, value_hash)` — a
shuffle-and-group, `O(N log N)` — never a pairwise cross-join. Blocking on
the identifier value first means R-04's extra name-compatibility predicate
only ever evaluates within a single (screened, usually tiny) block. This is
what makes the approach viable at the `large` profile's ~2M identifier
edges, even though that profile was not run in this environment (see
`benchmarks/RESULTS.md`).

## Data model normalisation

See `docs/DATA_DICTIONARY.md` for the full table-by-table detail. Summary
of the three groups from §12.1: core domain (3NF, FK-constrained),
analytical/serving (`customer_metrics`, `agg_*` — denormalised, disposable,
