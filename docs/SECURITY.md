# Security

## Threat model (brief)

- **Who might attack this:** an authenticated low-privilege user probing
  for horizontal/vertical privilege escalation; an unauthenticated caller
  probing the public surface (`/auth/login`, `/health`); a credential-theft
  scenario against the stored password hashes.
- **Not in scope for this v1:** DDoS/rate-limit-at-scale, network-layer
  attacks (TLS termination is assumed to sit in front of this in any real
  deployment), multi-tenant isolation (single-tenant model).

## Authentication

- Argon2id password hashing (`argon2-cffi`), never a faster/weaker hash.
- JWT access tokens (15 min default TTL) and refresh tokens (7 day
  default), `HS256`, secret from `JWT_SECRET_KEY` — the app **refuses to
  start** without a real secret (`c360/config.py`'s startup validator
  rejects an empty or placeholder value).
- Refresh token reuse detection: each refresh token's `jti` is stored
  hashed in `refresh_tokens` with a `family_id`; a request bearing an
  already-revoked `jti` revokes the entire family (`/auth/refresh` in
  `c360/api/v1/auth.py`).

## Authorisation (RBAC)

Four roles, strictly ordered: `viewer < analyst < data_engineer < admin`
(`c360/security/rbac.py`). Every endpoint declares its minimum role via
the `require_role(...)` FastAPI dependency — enforcement is server-side on
every request, never inferred from what the frontend chooses to render.

## Field-level masking

`c360/security/masking.py::apply_profile_masking` masks `primary_email`
and `primary_phone` server-side for roles in `MASK_PII_ROLES` (default
`analyst,viewer`) before the response is serialised — masking never
happens in the browser, and the raw value is never sent to a masked role
in the first place.

## SQL injection

All SQL lives in `c360/repositories/*.py` and `c360/segments/compiler.py`,
using SQLAlchemy's `text()` with **named bound parameters** exclusively —
no f-string or `%`-interpolation of any request-derived value into SQL
text anywhere in the codebase. The segment rule compiler
(`c360/segments/compiler.py::compile_ast`) is the sharpest case: a value
from a user-authored rule AST becomes a bound parameter (`%(p0)s`, …)
generated by the compiler itself, never a string splice — this is a
structural property of the compiler, not input sanitisation.

## Configuration safety

`Settings` (`c360/config.py`) validates at startup and refuses to boot on:
a missing/placeholder `JWT_SECRET_KEY`; `ENABLE_DOCS=true` in `prod`;
`CORS_ALLOWED_ORIGINS=*` in `prod`.

## What was designed but not implemented

- **Audit logging of every profile read/export** (§G-27): the
  `audit_logs` table and `write_audit_log()` repository function exist and
  are used for login events; they are not yet called from the
  profile/export read paths.
- **Rate limiting** (`slowapi`) is a declared dependency but not wired into
  `c360/main.py` in this session.
- **Security headers** beyond `X-Content-Type-Options`/`X-Frame-Options`
  (e.g. a CSP) were not added.

These are listed here rather than silently omitted — see
`docs/PROJECT_DECISIONS.md` for the full gap list and rationale.

## Frontend token handling

The access token is held in memory only (a module-level variable in
`src/lib/api.ts`); the refresh token is currently kept in
`sessionStorage` for simplicity, **not** the `HttpOnly` cookie the plan
recommends as the production-safe default. This is a stated trade-off:
`sessionStorage` is readable by any script on the page (XSS risk), whereas
an `HttpOnly` cookie would require the API to set it directly on
`/auth/login`/`/auth/refresh` responses and the frontend to send
credentials with `withCredentials: true`. The change is small but was not
made in this session — tracked in `PROJECT_DECISIONS.md`.
